# Stage C: asynchronous S3 secondary copy

v1.46.0.4.2.D keeps Postgres and MinIO as the authoritative primary storage.
After `upload_workflow_run_artifacts` confirms a primary object, it enqueues the
existing ARQ/Redis worker to copy the exact MinIO bytes to S3. The copy is
best-effort and bounded to three attempts; S3 errors never change call
finalization, disposition, Agent Run creation, or Simulation completion.

## Local defaults

`ENABLE_AWS_S3_SECONDARY=false` is the default. Localhost therefore makes no S3
requests and remains isolated to its Docker Postgres, Redis, and MinIO services.

## Future AWS configuration

Configure these in the deployment environment only:

```text
ENABLE_AWS_S3_SECONDARY=true
AWS_REGION=eu-west-2
AWS_RECORDINGS_BUCKET=<private-bucket>
AWS_S3_PREFIX=<optional-prefix>
```

The AWS SDK uses its normal credential provider chain (for example an EC2
instance profile or ECS task role). Do not commit access keys. The bucket should
remain private and use its normal server-side encryption policy.

## Audit events

`storage_audit.finalized` retains the Stage B primary result and adds the S3
secondary state: `disabled`, `not_configured`, `not_expected`, `pending`,
`success`, or `failed`. Each completed object copy emits
`storage_audit.s3_replication` with the run ID, bucket, source key, destination
key, attempt, and safe status/error class. Transcript text, audio, credentials,
and tokens are never logged.

S3 keys preserve the MinIO logical key by default. `AWS_S3_PREFIX`, when set,
is prepended without changing the primary MinIO key. Only artifacts confirmed
successful in MinIO are scheduled for replication.
