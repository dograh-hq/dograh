## Overview

The Roark integration node sends each completed call to [Roark](https://roark.ai) once the call finishes. Roark stores the recording, keeps the transcript and tool calls Dograh captured, and runs your metrics over them, so you can score agent behaviour and watch quality trends without writing any code.

The node is export-only. It takes no part in the conversation, adds nothing to the live call path, and does its work after the call has already ended.

## Prerequisites

- A [Roark account](https://platform.roark.ai) with a project
- A Dograh voice agent workflow
- A Dograh deployment Roark can reach (see [Reachability](#reachability))

## Setup

### 1. Create a Roark API key

In Roark, open **Settings → API Keys** and create a key for the project the calls should land in. The key decides the project; there is nothing to configure on the Dograh side for that.

The key needs permission to create calls, and to create agents if you want Dograh to register the agent for you.

### 2. Add the Roark node to your workflow

In the workflow editor choose **Add node**, scroll to **Integrations**, and select **Roark**. The node drops onto the canvas unconnected, which is correct: it is configuration, not a conversation step.

### 3. Configure the node

| Field | Required | What it does |
|---|---|---|
| **Roark API Key** | Yes | The project key from step 1. |
| **Roark Agent Name** | One of these two | The agent's name in Roark. Roark reuses an agent with this exact name in the project, or creates it on the first call. |
| **Roark Agent ID** | One of these two | The UUID of an agent that already exists in Roark, as shown in the Roark dashboard. Takes precedence over the name, and is rejected on save if it is not a UUID. |
| **Send Dograh transcript** | No, on by default | Send the turns and tool calls Dograh captured. Off means Roark transcribes the recording itself and receives neither. |
| **Send gathered context** | No, off by default | Also send the variables the agent gathered as Roark call properties. |
| **Enabled** | No, on by default | Turn the export off without deleting the node. |

Use **Roark Agent Name** unless you already have the agent in Roark and want to be certain the calls attach to it. Setting a name that does not exist yet is the zero-setup path: the agent appears in Roark the first time a call lands.

Choose **Save**, then **Publish** the workflow.

<Warning>
  Inbound calls always run the **published** version of a workflow, never the
  draft. If the Roark node only exists in your draft, calls will connect and
  the conversation will happen normally, but nothing will ever reach Roark.
</Warning>

### 4. Verify

Make a test call through your agent. When it completes, the call appears in Roark under the agent you configured. Its **External ID** is `dograh-run-<id>-<install>`, where `<id>` is the Dograh run.

If nothing arrives, open the Dograh run and look at its annotations: every attempt records its outcome under a `roark_<node id>` key, including the message Roark replied with. A node that was misconfigured records `validation_failed` with the fields to fix, so you do not need access to the server logs.

## What Dograh sends

One `POST /v1/call` per completed run. A workflow holds at most one Roark node, so a run is exported at most once.

| Roark field | Where it comes from |
|---|---|
| `recordingUrl` | The run's mixed-track recording, behind its public download token |
| `startedAt` | The first event recorded in the call |
| `interfaceType` | `WEB` for a browser call, `PHONE` for a telephony call |
| `callDirection` | The run's inbound/outbound call type |
| `endedStatus` | Mapped from `call_status`, the mechanism Dograh observed the call end by |
| `agent` | The agent name or ID from the node |
| `customer` | The caller's number inbound, the dialled number outbound |
| `transcript` | Final user transcriptions and bot turns, with offsets |
| `toolInvocations` | Function calls the agent made, with arguments and results |
| `externalId` | `dograh-run-<id>-<install>`, the run id plus a fingerprint of the install |
| `properties` | Dograh run, workflow, definition, campaign, status and disposition identifiers |

### Call properties

Every export carries `dograh_workflow_run_id`, `dograh_workflow_id` and `dograh_run_mode`, which you can filter and group on in Roark. The rest ship when the run has them: `dograh_workflow_name`, `dograh_definition_id`, `dograh_campaign_id` on a campaign call, and `dograh_call_status`, `dograh_call_disposition` and `dograh_mapped_call_disposition` once the call has been dispositioned.

`dograh_call_status` is how the call ended and `dograh_call_disposition` is what came of it. They hold the same value until something records an outcome: an end-call tool, a transfer, or disposition extraction.

Turning on **Send gathered context** adds the variables the agent collected during the call, each prefixed `dograh_context_`. It is off by default because gathered context routinely holds personal data, and Roark is a separate system with its own retention.

Two things to know if you turn it on. Roark fixes a property's type the first time it sees it, so a variable whose type changes between calls (a number on one call, a string on the next) is dropped on the calls that disagree. And a variable holding a list is stored as text rather than as a list you can filter per element.

### Transcripts

With **Send Dograh transcript** on, Roark grades the transcript Dograh captured during the call: what your speech-to-text actually heard and what your agent actually said. That is usually what you want, because it is what the agent reasoned over.

Turn it off to have Roark transcribe the recording with its own speech-to-text instead. The useful reason to do that is to compare the two, for example to measure your provider's accuracy against Roark's. Note that this also stops Dograh sending the call's tool invocations, which are read from the same event stream: Roark then has the audio and the call properties only.

<Note>
  Each turn is timed from when the speaking started, not from when Dograh
  logged it, so the transcript lines up with the recording in Roark's player.
  Offsets are measured from the first event in the call, because Dograh does
  not record the moment recording began; on measured calls that leaves the
  transcript around half a second ahead of the audio.
</Note>

## Reachability

Roark downloads the recording from your Dograh deployment rather than having it pushed, so the address it is given has to be reachable from the public internet.

Dograh resolves that address the same way it does for telephony webhooks: it uses `BACKEND_API_ENDPOINT` when that is publicly reachable, and otherwise falls back to the URL of a running [Cloudflare tunnel](/integrations/telephony/inbound). So a deployment on a laptop or inside a private network works as long as the tunnel is up:

```bash
docker compose --profile tunnel up -d cloudflared
```

With neither a public address nor a tunnel, the export is refused before it is sent and the run's annotations carry `recording_url_not_public` along with the host that was resolved. Roark fetches the recording asynchronously, so a private address would not fail the POST: the call would land in Roark and simply never get its audio.

The download URL is unauthenticated but unguessable: it carries the run's public access token, the same token QA and webhook exports use, and re-signs storage access on each request so it does not expire.

## Re-running an export

`externalId` is unique within a Roark project, so a run can only ever produce one Roark call. If the post-call job runs twice for the same run, Roark answers the second attempt with a 409 and Dograh records it as `duplicate` rather than as an error. Nothing is double-counted.

The ID carries a fingerprint of the install as well as the run id, so two Dograh deployments sharing one Roark project (a staging install alongside production, or a rebuilt database that restarted its run numbering) do not answer each other's calls as duplicates. The fingerprint is a hash of the run's public access token, which is generated once per run, so it is the same on every attempt at the same run.

## Limits

- **A call with no recording is not exported.** Roark ingests a call around its audio, so a run that produced none is skipped and recorded as `missing_recording`. A recording URL whose host is local or private is refused the same way, as `recording_url_not_public`; that is a reachability check on the address, not a fetch, so a public host that happens to be unroutable is not caught.
- **Text chat runs are not exported.** They have no audio, and Roark models a chat as a separate resource.
- **The export is not retried.** A refusal is recorded in the run's annotations with Roark's message; publish the fix and the next call exports normally.
- **Mono only.** Dograh keeps separate agent and caller tracks, but sends the mixed recording, so Roark separates speakers itself rather than reading them off channels.
- **A run deleted in Roark cannot be re-sent.** A deleted call keeps its external ID, so a fresh export of the same run is answered as a duplicate.
- **Tool results are sent as Dograh recorded them.** Dograh stores a tool's return value as its Python representation (`{'ok': True}`) rather than as JSON, and that string is what reaches Roark.
