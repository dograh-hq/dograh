Pre-Call Data Fetch lets you enrich the call context and select model settings before the voice agent starts. Configure it on the [**Start Call**](/voice-agent/start-call) node for every call, inbound calls only, or outbound calls only. Returned variables are merged into the call's [initial context](/core-concepts/context-and-variables#initial_context) and become available in prompts and greetings.

## How It Works

1. Dograh prepares the run using its selected workflow version.
2. Dograh sends a **POST** request to your endpoint. For outbound calls, this happens before dialing. For inbound calls, it happens before model services start.
3. Your API returns context variables, model overrides, or both.
4. Dograh resolves the organization, workflow, API-trigger, and fetched model settings in that order, then validates the final setup.
5. Dograh saves the resolved settings, checks billing and quota, and starts the call's model services.

## Configuration

Open the [**Start Call**](/voice-agent/start-call) node editor and expand **Advanced Settings**. Choose a **Pre-Call Data Fetch** mode and configure the endpoint when the mode is not disabled:

| Field | Description |
| --- | --- |
| **Pre-Call Data Fetch** | **Disabled**, **Always**, **Inbound calls only**, or **Outbound calls only**. Calls without an inbound or outbound direction run the fetch only in **Always** mode. |
| **Endpoint URL** | The URL Dograh will send the POST request to. |
| **Authentication** | Optional credential for authenticating the request. Supports API key, bearer token, basic auth, and custom header. |

## Request Format

Dograh sends a `POST` request with the following JSON payload:

```json
{
  "event": "call_inbound",
  "call_inbound": {
    "agent_id": 123,
    "workflow_run_id": 456,
    "from_number": "+12137771234",
    "to_number": "+12137771235"
  }
}
```

| Field | Description |
| --- | --- |
| `event` | Always `"call_inbound"`. |
| `call_inbound.agent_id` | The workflow (agent) ID. |
| `call_inbound.workflow_run_id` | The run ID used to prepare this call. |
| `call_inbound.from_number` | The caller's phone number (`caller_number` from initial context). |
| `call_inbound.to_number` | The called phone number (`called_number` from initial context). |

The `Content-Type` header is `application/json`. If you configured a credential, its authentication header is included. Caller and callee numbers are supplied when known during preparation; metadata assigned by the telephony provider after dialing is not yet available.

The request includes an `Idempotency-Key` header such as `dograh-pre-call-456`. Dograh saves the preparation result and reuses it on normal startup retries. A worker crash before saving can cause redelivery with the same key. Make your endpoint idempotent using this key if it performs writes or other side effects.

## Expected Response Format

Your API should return a **JSON object** with a `2xx` status code. The variables to inject into the call context should be placed inside the `initial_context` key:

```json
{
  "call_inbound": {
    "initial_context": {
      "customer_name": "Jane Doe",
      "account_status": "active",
      "loyalty_tier": "gold",
      "open_tickets": 2
    }
  }
}
```

You can also place `initial_context` at the top level:

```json
{
  "initial_context": {
    "customer_name": "Jane Doe",
    "account_status": "active"
  }
}
```

<Note>
The legacy `dynamic_variables` key is still accepted as a drop-in alias for `initial_context`, so existing integrations keep working without any changes. Use `initial_context` for new integrations. If a response contains both keys, `initial_context` takes precedence.
</Note>

After the response is received, you can reference these values anywhere template variables are supported:

- **Greeting**: `Hello {{customer_name}}, thank you for calling!`
- **Prompt**: `The customer is a {{loyalty_tier}} member with {{open_tickets}} open support tickets.`

<Note>
If the response is not a valid JSON object, or the request fails or times out, the call continues using its earlier context and model settings. A response without context fields leaves context unchanged. An explicitly returned invalid `model_overrides` object fails validation and stops preparation.
</Note>

## Override models for this call

Return `model_overrides` beside `initial_context`, either at the top level or inside `call_inbound`:

```json
{
  "call_inbound": {
    "initial_context": {
      "customer_name": "Jane Doe"
    },
    "model_overrides": {
      "model_configuration_uuid": "11111111-1111-4111-8111-111111111111",
      "llm": {
        "settings": {
          "temperature": 0.2
        }
      },
      "tts": {
        "settings": {
          "voice": "default"
        }
      }
    }
  }
}
```

Replace the UUID with an active named model configuration in the same organization, and use a voice supported by its selected TTS provider. You may return only `model_overrides` when no context enrichment is needed. If you use the `call_inbound` envelope, put both fields inside it.

Fetched model settings take precedence over workflow and API-trigger settings. Selecting a named configuration starts from that entire saved setup; omit its UUID to patch the already-selected setup. A service may also select a `provider_connection_uuid`. The same-provider and different-provider connection rules match [API trigger overrides](/voice-agent/api-trigger#choosing-models-for-one-call).

Overrides cannot change credentials, connection endpoints, organization identity, or billing metadata. Unknown fields, missing or unrelated UUIDs, incompatible indexed-document embeddings, and incompatible service selections stop preparation. Settings are validated locally without testing credentials against model providers. The resolved settings are saved for this run and do not modify your named configurations.

## Nested Variables

If your `initial_context` contains nested objects, you can access them using dot notation:

```json
{
  "call_inbound": {
    "initial_context": {
      "customer": {
        "name": "Jane Doe",
        "address": {
          "city": "Los Angeles"
        }
      }
    }
  }
}
```

Access in prompts as `{{customer.name}}` and `{{customer.address.city}}`.

## Timeout

The request has a **10-second timeout**. If your API does not respond within this window, the call proceeds without the fetched data. Respond quickly to minimize the delay before dialing or starting the agent.

When a real phone call comes in, the `caller_number` and `called_number` context variables are automatically set by the telephony provider and included in the pre-call data fetch request as `from_number` and `to_number`. For **web calls** (WebRTC), there are no real caller and callee phone numbers, so provide test context if your endpoint requires them. Phone calls use the caller and callee information available during preparation.

To simulate telephony data during testing:

1. Open your workflow and go to **Settings**.
2. Under **Context Variables**, add the following variables:
   - `caller_number` — set to a phone number you want to simulate as the caller (e.g., `+12137771234`).
   - `called_number` — set to the number that would be dialed (e.g., `+12137771235`).
3. Save the settings.

Now when you make a web test call, these values will be sent in the pre-call data fetch request to your endpoint, allowing you to test the full flow as if a real inbound call were coming in.

<Note>
Use actual telephony numbers when present. Test context is useful for WebRTC calls that have no telephony metadata.
</Note>

## Example Integration

A simple Node.js endpoint that looks up a customer by phone number:

```javascript
app.post("/dograh/pre-call", async (req, res) => {
  const { call_inbound } = req.body;

  const customer = await db.customers.findOne({
    phone: call_inbound.from_number,
  });

  if (!customer) {
    return res.json({});
  }

  res.json({
    call_inbound: {
      initial_context: {
        customer_name: customer.name,
        account_status: customer.status,
        loyalty_tier: customer.tier,
      },
    },
  });
});
```
